# Delivery HUD · 只读蓝牙骑行仪表盘

给一台**育宁 72V 电动车**做的安卓 HUD：上车自动连控制器，整屏大字显示电压、电量、本次里程、续航、时速，按颜色预警，息屏不掉线。

所有数据只从控制器的 BLE **通知帧**里读，**不向控制器写任何指令**（全工程唯一的写操作是把 CCCD 写成 `01 00` 开通知，这是 BLE 标准订阅动作）。

## 界面

普通页一屏四格：

- **电压**（大字，带压降补偿后的端电压）
- **电量**（手机电池样式：圆角壳 + 壳内进度填充 + 壳内百分比，绿/黄/红）
- **本次里程**
- 下排：续航、时速、总里程、能耗 Wh/km

极简页只留电压 / 电量 / 本次里程三格，适合强光下扫一眼。

## 数据从哪来

| 显示项 | 来源 | 说明 |
| --- | --- | --- |
| 电压 | 控制器 67B 通知帧 | 每帧含原始电压与压降补偿值，取静置/带载两套口径 |
| 电量 | 静置电压查表 + 骑行段里程推算 | 见下节，这是本项目最麻烦的部分 |
| 续航 | 电量 ÷ 每公里耗电% | 每公里耗电由静置锚点之间学出来，上限受"满电续航"约束 |
| 本次里程 | GPS 位移优先、速度积分兜底 | 一条通道不重不漏；`<1km/h` 不计；长按清零 |
| 总里程 | App 累计 + 与车仪表对表 | 对表后按比例修正系数，不写控制器 |
| 时速 | GPS / 控制器 | 控制器无速度字段时标记 `GPS` |
| 能耗 | 能量守恒倒算 | 最近 1km 掉电% × 额定 Wh |

## 只读红线

这条是硬约束，做成了代码级守卫 + 自检脚本：

- **唯一写入口**是 `BleLink.writeCccdOnly()`，只写 `0x2902` 描述符的 `01 00`；
- 写别的特征/描述符会被拦下并打 `WRITE-BLOCKED` 日志；
- `python tools/check_no_write.py` 扫全工程，出现 `writeCharacteristic` / `executeReliableWrite` / `WRITE_TYPE_*` 直接判失败；
- `FFF5`（写特征）、`AE01`（AE00 服务的写无响应特征）**一次都没碰过**。

控制器没有电流传感器、没有 SOC 字段，也不给速度/里程，所以电量只能靠"停着量电压、跑着数里程"这条路。

## 电量口径

### 为什么不能每秒拿电压查表

端电压是噪声源：同一分钟内实测在 58–69V 之间跳；骑行时 500W 电机还会把电压压掉 3–6V。直接查表，电量就会 51% → 17% 地跳，骑手不敢信。

所以分三种状态：

| 状态 | 口径 |
| --- | --- |
| **停稳**（停稳 20s+、无油门、低速/P 档） | 电压查表，端电压≈开路电压，这时可信 |
| **骑行** | 按里程账本推算：`锚点电量 − 每公里耗电 × 里程` |
| **断开** | 冻结断开前最后一帧的读数，不按里程瞎猜 |

### 电压表（当前实际使用）

| 静置电压 | 78.6 | 77.3 | 75.9 | 74.9 | 74.0 | 73.3 | 72.6 | 72.1 | 70.6 | 66.3 | 63.8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 电量 | 100% | 94% | 87% | 78% | 70% | 63% | 50% | 41% | 28% | 15% | 0% |

设置页可以改"满电 / 欠压"两点重新线性标定整表。

### 补电式用法的三个补丁

用户的实际用法是**"骑一段回家插电补一会儿、再骑"**，从来不彻底充满。这套用法把"满电起算 + 里程扣减"的模型打穿了三次，对应三个修复：

1. **v1.0.67** — 开机满电判定收紧：必须连续 ≥6 帧、持续 ≥8 秒都在 `vFull−0.2` 以上才算满电，挡掉启动瞬间的电压尖峰把半电判成满电。
2. **v1.0.68** — 续航不再减"本箱已跑"（补电场景下这个坐标会累计到超过满电续航，把 94% 的续航压成 6km）；本箱里程超过满电续航时跳过能量体检；静置查表 ≥20% 且两次读数稳定在 5 点内，就整段落回电压口径。
3. **v1.0.69** — 三个入口一起收：
   - `predict()` 不再把"里程倒退"算成充电（对表/重启后本次里程变小，旧公式会算出 114% → 夹 100，这是"连上就九十多"的直接元凶）；
   - 上抬留账：每次往上抬记下抬到多少，之后静置电压低 10 点以上（40 分钟内）就整段落回，不再靠"每停一次降 4 点"慢慢蹭；
   - 断连 1 分钟以上再连上时，头 90 秒只接受往下的校准（刚拔充电器的表面电荷会读到 77–78V，查表 94%，真值只有 74.8V/78%）。

### 已知边界

- 骑行段仍走里程账本，带载压降 3–6V 不能直接查表；
- 末端（查表 <20%）保留"三次确认 + 3 点/次 + 12 点预算"的保守通道，防 11-17 那种末端电压塌陷导致"0% 还能骑十公里"；代价是真余量还有十几公里时可能提前报低；
- 控制器断电保护一旦触发，直接锁 3% / 续航 0，直到真充满才解；
- `est_range` 默认 80km，需要"真充满一箱骑到断电"才能由 `learnTrueRangeOnCutoff` 自动校准。

## 构建与自检

需要 JDK 17 + Android SDK（platform 34 / build-tools 34）：

```powershell
.\gradlew.bat :protocol:test :core:test    # 单测，秒级，不用手机
.\gradlew.bat assembleDebug                # 产物 app/build/outputs/apk/debug/app-debug.apk

python tools\self_check.py                 # 一键六项：红线 / protocol / core / 打包 / APK CRC / 版本一致
python tools\check_no_write.py             # 只查"有没有偷偷写控制器"，几毫秒
```

> 单测名是中文，控制台按 GBK 渲染会显示乱码，判定只看 `PASSED` / `FAILED`，或读
> `core/build/test-results/test/TEST-com.hud.core.CoreAlgorithmsTest.xml`。

## 装车使用

1. 安装 APK，授予**附近的设备 / 位置 / 通知**三项权限（缺蓝牙权限连不上）；
2. 设置页填控制器 MAC（或用 `yuning / 育宁` 这类设备名关键字兜底匹配）；
3. 回主页，2 秒内顶部出现 `已连接 · 0xFFF6 · x.xHz`；
4. 首次使用对一次表：把"总里程"改成车仪表上的读数，系数会自动修正；
5. 想改电量刻度就调设置里的"满电 / 欠压电压"，整表线性重标定。

**注意：微信小程序和这个 App 不能同时连控制器**（BLE 单连接），标定时先退出小程序。

## 已知坑

- **小程序占连接**：小程序不退，App 永远连不上（`status=133`）。
- **控制器用随机地址**：MAC 会变，必须靠"设备名关键字"匹配。
- **国产 ROM 杀后台**：加进"自启动 / 后台高耗电"白名单，否则息屏十分钟后被清。
- **开机自启可能被拦**：部分 ROM 会静默拒绝 `BOOT_COMPLETED`，首次开机手动点开一次。
- **GPS 兜底耗电**：1 秒 1 次定位；只用导航时可关掉定位权限，但时速会失去兜底。
- **压降不是掉电**：刚起步那几分钟电量偏低是正常的（方向对防推车有利），别拿带载电压校准。
