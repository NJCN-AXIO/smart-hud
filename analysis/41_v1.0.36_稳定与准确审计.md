# v1.0.36：以「稳定 + 准确」为准的整体复盘

这一轮不是加功能，是把代码重新当成别人的项目读一遍，只修"会算错、会卡住"的地方。

## 一、审计范围

按数据链路从头到尾过：BLE 链路（`NordicBleLink`）→ 帧解析（`:protocol`）→ 压降/查表（`LoadComp` / `SocModel`）→ 里程与时速（`TrackDistance` / `SpeedStabilizer` / `TripIntegrator`）→ 显示层（`BleService.tick` / `HudScreen`）→ 设置与持久化（`Prefs`）。

## 二、找到并修掉的问题

### 1. 满电静压默认值错了，这是"系统性低估电量"的结构性原因（准确性，重要）
- `Prefs.vFull()` 默认 **78.0V**，而那是**浮充电压**（6×13.0V，充电器在充电时给的电压），不是静置开路电压。
- `SocModel` 的参考表按 **76.5V = 100%** 建。两者错位后，查表前先被压缩一遍：
  `vRef = 63 + (v-63) × 13.5/15`。实测后果：满电静置 75.1V 会被映射成 ≈73%，越往下偏得越多，
  低端（69.6→63 那一段）几乎全被压进个位数——这正是"显示 4%、实际还能跑很远"的来源之一。
- 修：默认改 76.5；并加一次性迁移，只把"还是老默认 78.0"的用户改成 76.5，
  用户自己按实测标过的值（比如 75.6）一个不动。

### 2. 电量两位数跳变：加显示层中位数（准确性 + 稳定性）
- 电压已经滤过（`VoltFilter` 时间窗分位），但"电压→百分比"是查表，**低端很陡**：
  68.0V→66.0V 就差好几格，电压 0.3V 的正常抖动会放大成 5–10 个百分点；
  再叠加 `ocvCand`（45 秒窗）与瞬时值之间的来回切换，就出现"同一时刻 51% → 17%"。
- 修：新增 `:core.SocSmooth`（6 秒窗中位数，**接受 0**）。照 BMS 显示 SOC 的常规做法：
  对"算出来的百分比"取中位数，而不是对电压再滤一遍。单帧坏值压掉，真实变化最多慢 3 秒。
- 注意为什么不复用 `VoltFilter`：它把 `v <= 0` 当非法丢掉，而 0% 是合法电量。
- 新增 5 条单测（单帧离谱值、0 合法、真实下降跟得上、NaN 不清空、reset）。

### 3. 扫描可能"卡在扫描中"（稳定性）
- `connect()` 在"直连 3 次失败"后进 `startScan()`，而上一轮扫描的超时回调可能还没到点。
- 同一 `ScanCallback` 重复 `startScan`，部分机型直接回 `SCAN_FAILED_ALREADY_STARTED`；
  之后 `scanning` 一直是 true，`state()` 永远"扫描中"，表现就是界面一直转圈。
- 修：`startScan()` 先 `stopScan()`。

### 4. 被小程序抢走之后回到 App，还要干等几十秒（稳定性）
- 原来的阶梯退避（8/20/45/60 秒）是为了不跟小程序互踢，逻辑本身是对的。
- 但用户关掉小程序、回到这个 App 时，退避可能还剩几十秒 → 屏幕一直"连接中"。
- 修：`MainActivity.onResume` 里，若当前不是已连接，直接发一次 `reconnect`（10 秒内只发一次）。
  "人回到前台"本身就是"我现在要它"的信号，这时候抢一次是安全的。

## 四、明确留到下一轮（需要你的数据，不宜猜）

1. **低端表 69.6V→63.0V 这一段太陡**：63.0V 是"带载截止电压"，不是静置开路电压（静置 0% 大约 69.6V）。
   要改得靠你一次真实的"跑到欠压"日志，才敢动表。现在改就是拿猜的替换猜的。
2. **电压大数字是"这一帧原始值"**：会跟着控制器 2Hz 抖动（小程序也是这个口径）。
   要不要再上一档 3 秒中位数，取决于你更在意"和小程序逐帧一致"还是"眼睛舒服"，这个得你定。
3. 三个空壳 Java（`FieldMap` / `YuNingDecoder` / `Decoder`）仍是占位，删除需你点头。
