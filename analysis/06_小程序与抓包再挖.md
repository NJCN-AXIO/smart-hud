# 小程序那边还能挖什么：重新解了抓包，结论变了

## 1. 先把抓包重解了一遍（这次解析器修对了）

旧解析把 L2CAP 头的两个字段读反了（`length` 和 `cid` 调了个位置），
所以之前算出来的"通知 20 字节"其实是被截断的读数。修正后（`tools/capture_timeline.py`）：

| 项目 | 实测值 |
| --- | --- |
| 协商 MTU | **517**（不是 23） |
| FFF6 通知 | **91 条，每条都是 20 字节，内容完全相同** |
| 通知内容 | `C9 9C 94 05 59 59 69 59 6A 81 1E 4D 75 75 75 75 1D 1D 1D 1D` |
| 小程序写 CCCD | `01 00` → handle 0x000B（FFF6 的 CCCD，就是"订阅"） |
| 小程序写配置 | `00 10 00 18 00 0A 00 58 02`（9 字节）→ **handle 0x0807** |
| 小程序写查询 | 67 字节 `C9 9C 03 09 59 59 69 59 …` → handle 0x0008（FFF5），约每 4.5 秒一次 |

MTU 是 517，**所以那 20 字节不是被截断，它就是一条真的 20 字节帧**。
之前"20B 只是 67B 被 MTU 截出来的前缀"这个推断，错了。

## 2. 电压真的在那两个字节里

`[2..3] = 94 05` → `0x0594 = 1428` → `1428 × 0.05 = 71.4V`。

而 20:42 那张小程序截图，电池电压正是 **71.4V**；抓包是 20:36，中间十几分钟车没动。

五个锚点全部自洽：

| 截图电压 | 帧内 `[2..3]` | 小端值 × 0.05 |
| --- | --- | --- |
| 69.7 V | `72 05` | 69.7 |
| 71.4 V | `94 05` | 71.4 |
| 72.3 V | `A6 05` | 72.3 |
| 74.9 V | `DA 05` | 74.9 |
| 78.3 V | `1E 06` | 78.3 |

**所以 `[2..3] × 0.05` 就是电压，这件事已经不是"候选"了，是坐实的。**

## 3. 但我们为什么永远看到 71.4 而且 67B？

因为两边的对话方式不一样：

```
小程序：订阅 FFF6 → 每 4.5 秒写一个 67B 查询到 FFF5 → 控制器回 20B 遥测帧（带电压）
我们  ：订阅 FFF6 → 只读、不写        → 控制器一直推 67B 广播帧（[2..3] 冻在 94 05）
```

67B 那一型帧里，`[2..3] = 94 05` 在 36 分钟、3504 帧里一个 bit 都没动
（其余 61 个字节也不动，只有 5 个字节是噪声/标志/CRC）。

**结论：20B 遥测帧是"问"出来的，不是"推"出来的。**
被动订阅永远只能拿到那套没有实时电压的 67B 广播。

也就是说 —— 你定的那条红线（不给控制器写数据包）和"实时电压"是互斥的，
这一点现在有机制级的证据了，不是猜测。

## 4. 那 AE02 呢？

之前怀疑"订阅 AE02 会切帧格式"，现在证据弱化了：真正决定帧型的是**有没有发查询**。
不过 AE02 那条对照实验（设置里取消勾选）仍然值得跑一次，把疑问彻底清掉；
它已经不是主线，优先级降到最后。

## 5. 还有一个没被注意的东西：handle 0x0807

小程序连上后往 **0x0807** 写了 9 个字节：`00 10 00 18 00 0A 00 58 02`。

而这个 handle 我们从来没枚举到过（我们只看到 0x1800 / 0xFFF0 / 0xAE00 三组服务）。
它很可能是另一组服务（0x0800 区）里的"配置/使能"特征 ——
**这一条值得挖**：搞清它是什么，可能解释"上报周期""工作模式""要不要握手"。

## 6. 小程序源码：解密链路已经打通，但本机没有这个包

用公开方案实现了 PC 微信 wxapkg 解密（`tools/wxapkg_decrypt.py`）：

```
key = PBKDF2-HMAC-SHA1(appid, "saltiest", 1000, 32)
前 1024 字节 AES-256-CBC（IV = "the iv: 16 bytes"）+ 其余字节 XOR ord(appid[-2])
```

在 `%APPDATA%\Tencent\xwechat` 下扫了 **257 个 wxapkg**，解密成功、头字节校验通过，
但**里面没有育宁那个小程序**（PC 微信从没打开过它，只在手机上用过）。
所以想从代码里挖，得先让 PC 微信打开一次"育宁科技"小程序。

## 7. 所以"还能挖什么"的实际排序

| 值不值得挖 | 内容 | 能不能不写包拿到 |
| --- | --- | --- |
| ★★★ | 故障码文案（P档、刹车…）、参数页枚举（仪表协议 爱玛1、车型、超速档位） | 能（纯 UI 知识，直接抄进设置页/提示） |
| ★★ | `0x0807` 那 9 字节配置包的含义 | 只能读（枚举服务表即可知道它是什么特征） |
| ★★ | 小程序里有没有"电量%"算法 | 能（如果有，直接抄它的表） |
| ★ | 查询包 `C9 9C 03 09 …` 的字段结构 | 要写才用得上，红线内不用 |
| ✗ | 实时电压 | **必须发查询**，红线内拿不到 |

## 8. v0.7.2 顺手改的

`YuNingProtocol`：**收到 20B 帧且用户没手工配映射时，默认套 `[2..3]×0.05`**（原先返回 NaN）。
理由就是上面第 2 节那五个锚点；同时 `note` 写明"20B 帧 · 候选映射"，
单测锁死 71.4V。67B 帧仍然一律不出电压（那里是死值，出了就是假数）。
