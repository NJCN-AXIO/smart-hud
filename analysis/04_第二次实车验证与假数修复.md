# 第二次实车验证：两个结论（v0.6.8 → v0.6.9）

## 一、帧还是 67B，"只订 FFF6"的假设被推翻

三张截图底部都是：

```
扩展帧（67B，字段未标定）· 候选映射（未同刻验证）
帧 C9 9C 94 05 59 59 69 59 …(67B)
```

也就是说，即使 v0.6.5 起**只订阅 FFF6、完全不碰 AE02 的 CCCD**，控制器仍然推 67B。
→ 结论：**订阅组合不是帧格式的开关**。抓包里那个"20 字节"更可能是同一个 67B 包在
MTU 23 下的前缀（两者开头字节完全一致：`C9 9C 94 05 59 59 69 59`），
而不是另一种"带遥测的帧"。

顺带把这条也钉死：67B 帧里没有电压（2983 帧、61/67 字节全程恒定），
所以 `:protocol` 的提示文案从"字段未标定"改成**"扩展帧（67B，无电压字段）"** ——
不再暗示"再标定一下就有"，省得每次都要解释。

**要拿到实时电压，只剩"发写包查询"这一条，而你已经明确不做。** 所以这一项到此为止，
不再花时间在协议上挖。

## 二、真正的 bug：76.3V / 83% 是个"冻住的数"

对比两张截图：

| 截图 | 里程 | 电压 | 电量 |
| --- | --- | --- | --- |
| 第一张 | 15.1 km | 76.3 V | 83% |
| 第二张 | 18.3 km | 76.3 V | 83% |

多跑了 3.2 公里，电压和电量**一位都没动**。原因在代码里，不在控制器：

```
旧逻辑：没有实测电压 + 没学到 %/km
       → 直接把"上次手工录的那个数"当当前电压显示（SRC_MANUAL）
```

这不是"不准"，是**假数**——比显示 `--` 更误导，骑手会以为电还满着。这正是你说的
"电量百分比不准、跑完还有电"的根源之一。

### v0.6.9 怎么改

推算电压改成**跟着里程往下走**，而不是恒定：

```
当前电压 = 锚点电压 − 压降率 × 已跑里程     （最低夹到欠压 63V）
```

压降率两个来源：

1. **学过的**：两次手工锚点之间"掉了多少伏 / 跑了多少公里"。
   例：0km 记 76.3V，8km 记 74.9V → **0.175 V/km**，这是他自己那块电池的真实斜率，存起来长期用。
2. **没学过的**：`(满电 − 欠压) / 满电续航 = (78 − 63) / 80 = 0.1875 V/km` 兜底。

按这个推算，那两张截图对应的应该是：

| 里程 | 推算电压 | 电量 |
| --- | --- | --- |
| 15.1 km | ≈ 73.5 V | ≈ 65% |
| 18.3 km | ≈ 72.9 V | ≈ 58% |

而不是 76.3V / 83%。`还能跑`也会跟着从 66km 掉到 ~45km —— 这才是"电真的在少"。

界面同时把"这个数是怎么来的"写清楚：底部会变成
`推算（锚点 12 分钟前 · 0.19V/km）`，电量下面写 `按推算电压（随里程下降）`。

## 三、下次怎么用更准

压降率是随车、随电池、随载重变的，所以最准的是**两三次手工锚点**：

1. 充满电、车停着 → 点「电压」，输 78.3（或小程序上看到的数）；
2. 跑 8–15 公里、停车 → 再点一次，输当时小程序上的数；
3. 之后 App 自动按学到的 V/km 往下推，不用每次都记。

每多记一次，斜率就更贴近你的车。
