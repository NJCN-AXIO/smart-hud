# 77 v1.0.69：补电浮电把电量抬到 94%，以及"上抬留账"

## 一、v1.0.68 之后还漏了一处

v1.0.68 删掉了"满电续航 − 本箱已跑"的续航硬顶，截图里"94% / 6km"的矛盾已经不可能再出现。
但把 11-26 的两份日志逐帧对齐后，能看到另一个更靠前的入口：**电量本身会被浮电抬到 94**，
而 v1.0.68 只修了"账本偏高时怎么落下来"，没修"账本是怎么升上去的"。

### 证据 1：10:23:56 起，十九秒从 45% 爬到 84%

```
[10:23:56] SOC 45 -> 47  vm=75.15 rv=75.25 sag=0.00 thr=0.76 spd=0
[10:23:57] SOC 47 -> 49  vm=75.18 ...
...
[10:24:12] SOC 78 -> 80  vm=75.23 ...
[10:25:09] SOC 82 -> 84  vm=75.54 ...
```

每秒 +2 点，target 就是 `75.2V → 查表 84%`。此后：

```

[14:26:21] SOC 58 -> 60  vm=76.32 rv=78.01 sag=0.00
```

依据是 77.3–78.0V。而 15 分钟后真静置只有 **74.8V（78%）**，14:33 / 14:43 两次校准都只肯往下 4 点：

```
[14:33:03] SOC 94 -> 92  vm=74.45 ...
[14:33:04] SOC 92 -> 90 ...
[14:33:05] SOC 90 -> 88 ...        ← 88 就停住了
[14:43:42] soc anchored at rest v=74.9 soc=78 km=18.90   ← 与账本 85 差 7 点，仍未整段
```

## 二、根因

1. **补电后的表面电荷（浮电）被当成 OCV**。充电器拔掉后十几分钟内，静置读数是 77–78V，
   查表 94%；真 OCV 要等表面电荷散掉才是 74.8V（78%）。控制器只给电压，分不出这两种状态。
2. **向上抬没有账**。抬错了之后，只能靠"12 点死区 + 三次确认 + 4 点/次 + 12 点预算"往下蹭，
   蹭下来之前屏幕一直写 94%、续航一直按 94 算 —— 用户就是在这段窗口里出门的。
3. v1.0.68 把向上的整段门槛放宽到 20 点（为了修"补电后电量偏低"），**反而给了浮电更大的抬升空间**。

## 三、改动（v1.0.69 只做两件事）

### 1. 上抬留账：`SocTracker.upMarkSoc / upMarkMs`

每次向上抬（整段或 `upStepPct` 步进）都记下"抬到了哪个值、什么时候抬的"。
下次静置若电压比这个值低 ≥ `upBackPct = 10` 点、且距上抬 ≤ `upBackWindowMs = 40 分钟`：

- **整段落回电压口径**，不走三次确认、不做 4 点慢挪；
- 这笔回落照样记进 `nudgedTotal`（夹到 `nudgeBudgetPct`），"一箱电纠偏有总额度"这条契约不破；
- `rejects` 清零，`lastLowSoc` 清空。

`resetNudgeBudget()`（满电）与 `hardLand()`（控制器断电）都会清掉这笔账。
40 分钟以外的旧账不翻 —— 那时候电压变低多半是真实掉电，该按里程走。

### 2. 重连初期只许向下：`BleService.linkBackMs`

断链 ≥1 分钟再连上时记下时刻，之后 90 秒内的静置校准若比账本高就跳过，日志：

```
soc calibrate skipped: link just back 42s, rise 58->94 not trusted (v=77.8)
```

往下永远安全，所以只有"向上"被挡。
