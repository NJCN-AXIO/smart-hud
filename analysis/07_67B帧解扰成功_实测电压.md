# 07｜67B 帧解扰成功：实测电压终于解出来了（v0.8.0）

> 一句话：过去所有"67B 帧里没有电压"的结论，都是**只看原始字节、没解扰**造成的误判。
> 育宁小程序的 67B 帧从第 4 到第 65 字节全部是加扰过的，按它的公式还原后，
> 电压、转把电压、故障位全都在里面。**读通知就能拿到，不需要向控制器写任何数据。**

---

## 1. 之前为什么一直解不出来

三个坑叠在一起：

| 坑 | 表现 | 真相 |
|---|---|---|
| 帧被截断 | 抓到/记到的都是 20B | 20B 只是 67B 帧的前 20 个字节，电压在第 63/64 字节，根本没到 |
| 字段被加扰 | 3504 帧里只有 `[42][47][63][64][65]` 五个字节在变，读原始值全是 30~90 的鬼数 | 4..65 字节整体做了四步变换，不解扰读到的都是垃圾 |
| 锚点巧合 | v0.7.2 曾用 `[2..3]×0.05` 得 71.4V，和截图吻合 | `[2..3]` 在每一帧里都是 `94 05`，恒定值，不是电压（已推翻） |

## 2. 还原公式（来自育宁小程序 `onBLECharacteristicValueChange`）

```
校验：raw[0] == 0xC9(201)、raw[1] == 0x9C(156)、raw[66] == 0xCC(204)、长度 67
还原：for (e = 4; e <= 65; e++) {
          f[e] = f[e] - 11
          f[e] = 85 ^ f[e]        // 0x55
          f[e] = f[e] - e
          f[e] = 19 ^ f[e]        // 0x13
          f[e] = f[e] - e
      }
```

## 4. 实车 3504 帧验证（`raw_20261117_141147.csv`）

- 3504 帧全部 67B、帧尾全 CC → **100% 通过校验**
- 电压 66.0 – 76.1V，**3504/3504 落在 30–100V 合理区间**
- 首帧 73.9V → 末帧 71.6V（跑了约 45 分钟，掉 2.3V，符合 72V21Ah 铅酸的放电曲线）
- 整 V 分布：75V×1273、71V×450、73V×440、72V×418、69V×216、74V×210、76V×260、70V×185、68V×30、66V×19、67V×3
- 故障位：`0x20`×2750（无故障/空位）、`0x22`×646（刹车）、`0xA0`×108（P档）

**结论：这不再是"猜测的映射"，是可复现、可对表、3504 帧全通过的实测通道。**

## 5. 落地到代码（v0.8.0）

`:protocol`

- `YuNingProtocol.unscramble(raw)`：上面那套四步逆变换（只处理 4..65）
- 67B 帧：校验长度 67 + 帧尾 CC → 解扰 → 电压 / 转把 / 故障位 / 型号
- 20B 帧：默认**不出数**（`"20B 短帧（需完整 67B）"`），只有用户在设置里手工填了字段映射才按他填的读
- 单测 11 条，其中锁定实车首帧 **73.9V / 转把 0.8V / P档 / note 含"实测电压"**，另加"帧尾不是 CC 就不出数"

`:app`

- `BleService.onNotify`：解出电压 → `liveV` → 界面走 `SRC_BLE`（底部写"实测电压"）
- 同一帧的故障位 → `HudState.faultsText`，界面在底部多一行 `控制器：刹车·P档`（琥珀色）
- 电量：`SocModel.soc(liveV)` 按电压表内插，**不再依赖手填/推算**
- 8 秒没有新帧才回落到手填/推算 —— 断开时不会假装还连着

## 7. 还没拿到的：时速

67B 帧里**没有速度字段**。证据：3504 帧里原始字节只有 `[42][47][63][64][65]` 五个在变，
解扰后分别是转把 / 故障 / 电压（`[65]` 未使用）。小程序 WXML 上的"实时转速"没有对应的
JS 赋值，控制器这一路通知不带宽速。

所以时速继续用成熟方案：GPS（OpenTracks 口径）——50m 精度门、10m 死区、5m 未知速度、
200m 跳点剔除，`OneEuro` 0.4Hz/β0.02/1.0Hz 滤波 + 0.6s 归零/4s 保持。
这条已有 42 条 `:core` 单测锁定。
