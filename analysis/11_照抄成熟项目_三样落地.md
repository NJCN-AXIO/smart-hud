# 11｜照着成熟项目抄了三样（v0.9.3）

这轮不是自己拍脑袋想功能，而是拿三个已经在跑量、被大量用户长期使用的项目做对照，
只挑"人家验证过、我们缺、且不需要买配件/接线/写控制器"的。

## 1. 连接参数：申请 HIGH 优先级（来自 Nordic 官方库文档）

**出处**：[NordicSemiconductor/Android-BLE-Library · Notifications and Indications](https://deepwiki.com/NordicSemiconductor/Android-BLE-Library/3.2-notifications-and-indications)
原文意思很直接：高频通知场景应当申请更高连接优先级以降低延迟；
社区的 Android BLE 长连接实践也在同一处给出 `requestConnectionPriority(CONNECTION_PRIORITY_HIGH)`
（约 11.25–15ms 间隔，比系统默认的省电间隔更密）。

**为什么这对我们重要**：控制器 1.9Hz 推 67 字节帧。如果系统把连接间隔给到 30–50ms，
一帧要拆成多个连接事件传完，偶发就会堆积、延迟抖动，甚至因为对端超时判断失误掉线——
这正好对上用户反馈的"多次断开重连、不稳定"。

**本次落地**：`NordicBleLink.onDeviceReady` 里由 `ControllerManager.raisePriority()` 发起，
日志写 `PRIORITY HIGH` / `PRIORITY-FAIL status=…`，接车后一眼能看出生效与否。

**红线检查**：这是本地链路参数申请（`BluetoothGatt.requestConnectionPriority`），
不改控制器任何状态，不产生任何写特征值的包。`check_no_write.py` 仍通过。

## 2. 语音播报（来自 OpenTracks 的 voice announcements）

**出处**：[OpenTracks（F-Droid 页面 · Features 列 "Voice announcements"）](https://eikectrlaltcoop.gitlab.io/fdroid-website/en/packages/de.dennisguse.opentracks/)

OpenTracks 是骑行/徒步记录里最成熟的开源项目之一，它把"关键数据用听的"当成标配功能——
因为骑行中看屏本来就是危险动作。我们的场景更极端：外卖骑手边骑边看导航，
低头看电压那一秒就是风险。

**本次落地**：
- 每 **5 公里**报一次「已行驶 X 公里，电量百分之 X」
- **低电**时（与震动同一时刻，5 分钟最多一次）报「电量不足，还剩百分之 X，请尽快充电」
- 用系统自带 `TextToSpeech`：不联网、不需要任何额外权限
- Android 11+ 必须声明 `<queries><intent><action android:name="android.intent.action.TTS_SERVICE"/></intent></queries>`，
  不声明会直接"找不到引擎"——这一步很多项目栽过
- 没有中文语音包 / 引擎初始化失败 → 记 `tts init failed` / `tts ready=false` 后**静默降级**，不影响任何主功能
- 设置里有开关，改了会重启一次服务让它生效

## 3. 防烧屏（DigiHUD 官方 FAQ 亲口承认的坑）

**出处**：[DigiHUD Speedometer · FAQ](http://digihud.co.uk/blog/frequently-answered-questions/about/)
官方原话：长时间显示静止画面会造成不可逆的烧屏，作者自己一台测试机
（Samsung Galaxy S3）跑了两三年后已经出现轻微黄斑。

DigiHUD 是这个品类里最老牌的 HUD 应用，这个结论来自它的长期实测——
比我们自己推测"OLED 可能会烧"可靠得多。这也说明 v0.9.2 的 90 秒挪 3dp 方向是对的，
本轮把它保留下来并在文档里记清依据。

## 4. 看过但**明确不抄**的（附理由）

| 项目/特性 | 为什么不抄 |
|---|---|
| DigiHUD 的 **HUD 镜像模式**（水平翻转投到挡风玻璃） | 我们是绑在车把上正着看，镜像等于把字反过来，直接不可读 |
| DigiHUD 的**浮动窗** | 骑手不会一边开别的 App 一边看仪表；浮动窗还会挡住导航 |
| OpenTracks 的 **GPX/KML 导出** | 我们要的是"这一趟跑了多少"，CSV 已经够；GPX 是运动记录用途 |
| OpenTracks 的**蓝牙心率/踏频/功率传感器** | 需要买配件，用户明确不买 |
| Android 官方建议的 **autoConnect=true 后台重连** | 实测这台控制器"自动连"会拖 30 秒以上，我们已有的"直连 3 次 + 扫描交替"更快更可控 |

## 5. 验证

- `:core` 50 / `:protocol` 11 单测全过
- 红线：唯一写仍是 CCCD `01 00`（`check_no_write.py` 通过）
- `self_check` 6 项全过；APK vc30 / 0.9.3；`local=142 central=142`、`testzip=None`
- 接车待验：日志中 `PRIORITY HIGH` 出现一次；断连次数应下降；
  `tts ready=true`；跑到 5 的整数倍时听到播报；低电时听到告警

## 6. 还剩什么（诚实清单）

- **时速/里程的物理上限**：67B 帧里 3504 帧只有 `[42][47][63][64][65]` 在变，
  **没有找到时速或轮速字段**，所以时速只能来自 GPS。想在隧道里也有速度，只能加速度计推算，
  误差比 GPS 更大，不做。
- **电池口径**仍未与你对齐成正式参数表（满电 78.0V / 欠压 63.0V / 满电续航 70–80km 是估值）。
  这个不改，电量百分比就永远带一个系统偏差——但只要偏差稳定，颜色预警依然有效。
