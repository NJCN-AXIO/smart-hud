## 2. 帧：还是 67 字节，而且这次能证明"订阅方式根本不是开关"

这次日志第一行就写着：

```
subscribe ae02 = true
SUBSCRIBE-PLAN  0xFFF6 > 0xAE02
```

**AE02 开关是勾上的。** 也就是说上一轮我根据三张截图下的结论（"只订 FFF6 仍然 67B"）
**不成立** —— 那次其实也是 AE02 开着跑的，对照实验从来没真正做过。这里更正。

那这趟给出了什么新事实？

| 项目 | 结果 |
| --- | --- |
| 帧长度 | 3504 帧**全部 67 字节** |
| 来源 | 全部 `0xFFF6`（AE02 一条通知都没有） |
| 不同帧 | 2142 种 / 3504 帧 |
| 真正在变的字节 | 只有 `[42] [47] [63] [64] [65]` |

逐字节统计（`analysis/ride_141147.txt`）：

| offset | 取值个数 | 行为 |
| --- | --- | --- |
| 42 | 132 | 大部分时间是 `0x49`，偶发跳到随机值（1933/3503 次相邻差为 0）→ 噪声/采样抖动，不是物理量 |
| 47 | 3（`0x69` / `0x2F` / `0xE9`） | 高位成块翻转 → 状态标志位 |
| 63 | 4（`0xE6` 为主，偶见 `0xDD/0xE7/0xE8`） | 校验相关 |
| 64 / 65 | 207 / 256 | 典型的 CRC/随机填充（256 个值全覆盖） |

`[2..3] = 94 05` 从头到尾没动过（这一对曾被当成"71.4V"的候选映射，再次被证伪）。

**结论：67B 帧里没有电压，也没有能直接当里程/时速用的字段。**
而且 AE02 勾着也是 67B → **订阅组合不影响帧格式**，抓包里那个"20 字节"
就是同一个 67B 包在 MTU 23 下被截断的前缀（开头 8 个字节完全一致）。

## 6. v0.7.1：把"断开后卡在扫描"这个坑填了

日志里的现象：`连接失败(status=-5)` 连撞几次之后，就变成每隔 15 秒一条
`conn: 扫描附近设备…`，直到某个瞬间（日志里 `picked 11:22:33:44:55:66`）才回来。

根因在代码里，一行判断写死了：

```java
// 老逻辑
if (connectFails < 3 && !lastMac.isEmpty()) { 直连 } else { 扫描 }
```

`connectFails` 只在"连上成功"或"扫描命中"时才清零，所以**一旦连撞 3 次，就永远走扫描分支**——
明明 MAC 还在、车就在旁边，却要等 12 秒扫描超时、再等 3 秒才动作一次。

v0.7.1 改成 **直连 3 次 → 扫描 1 次 → 再直连 3 次…** 的交替：

- 有 MAC 时先直连（200ms 就出手，快）
- `directAttempts >= 3` 才插一次扫描（扫描的作用是刷新系统里这个设备的连接状态，
  对已经吃满 133 的 GATT 比硬撞更有效）
- 扫描结束（不管有没有扫到）**`directAttempts` 归零**，回到直连优先
- 133 之后单独等 **4 秒**（原来 2 秒），给两边把旧 GATT 收干净的时间

效果：断开后最多 3 次直连 + 1 次扫描就会重新撞上，不用人再去设备列表点一遍。

另外把 `NordicBleLink` 里两处过时注释改掉了（原来写着"订 AE02 会变成 67B 模式"、
"不订它就和小程序一样拿 20B 帧"），改成实测结论，避免以后照着错注释改代码。
