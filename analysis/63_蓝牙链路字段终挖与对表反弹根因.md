# 63 蓝牙链路能拿到什么：60,364 帧字段终挖 + 对表反弹根因

## 背景（1.0.58 之后的新反馈）

- App 总里程比车上仪表偏多。
- 用户重新明确产品定位：**不需要 App 一直开着记录**，而是**随时打开 App 就能看到准确的剩余电量%、电压、总里程**；电压对齐小程序，总里程对齐仪表；电量由稳定电压 + 里程推算。

本轮先回答一个前提问题：控制器蓝牙链路到底能不能直读速度、里程、电量。若读不到，"总里程与仪表同步"就只能走对表基准 + GPS 增量估算，不存在自动读表的通道。

## 素材与方法

- 14 份 `raw_2026112*.csv`，解析出 **60,364 帧** 合法 67B 广播帧（`size==67 && raw[66]==0xCC`），**34,027 条 REC 快照**。
- 探针：`tools/frame_field_probe.py`。按小程序逆变换解扰 `f[4..65]`；逐字节统计取值范围/取值个数，并与就近 REC 的 GPS 速度算皮尔逊相关；两字节组合 LE/BE 做全程单调递增 + 小正增量扫描（另在临时探针里复核三/四字节）。

## 结论一：广播帧里没有速度、里程、电量字段

解扰后逐字节：

| 字节 | 含义 | 观测 |
|---|---|---|
| f[42] | 转把电压 | 与 GPS 速度 r=**+0.717**，唯一和动力相关的变量 |
| f[47] | 故障位 | r=**−0.468**（P 档/故障状态） |
| f[61] | 0/16 两值 | 状态位，语义未明 |
| f[63]/f[64] | 电压高/低字节 | `(256*f[63]+f[64])/100`，已验证 66.0–76.1V |
| 其余 60 字节 | 常量 | 配置项：72V、自动 P 档 30 秒、爱玛 1、低电平刹车、5 档、码数 100%、M1 等 |

- 两字节 LE/BE 单调扫描：命中的组合**全是常量对**（中位增量 0），没有任何全程单调递增、增量像里程表的字段；三/四字节复核同样 0 命中。
- 通知通道全程只有 **0xFFF6**；FFF5（props 0xe = READ/WRITE/NOTIFY）静默。
- 历史笔记 `analysis/06`：小程序每 4.5 秒向 FFF5 **写一个 67B 查询包**（`C9 9C 03 09 …`）才换回 20B 遥测帧；被动订阅只拿到 67B 广播。**这条旁路需要向控制器写数据包，触碰既定红线（只允许 CCCD `01 00` 开通知），未实现、未验证 20B 回帧里是否带速度/里程。**

## 结论二：小程序本身也不显示里程/时速/电量%

11-24 07:58 同屏截图对照：

- 小程序 Y14：电池电压 69.6、转把电压 0.8、故障 ",P档"，外加一排配置按钮；**没有速度表、没有里程表、没有电量百分比**。
- 仪表上的里程、时速、剩余电量是**控制器本地按霍尔/电压算后显示在仪表盘上的**，不走蓝牙广播。

因此：

| 数据 | 蓝牙能否直读 | App 现状口径 |
|---|---|---|
| 电压 | 能（f[63][64]） | 与小程序同帧同源，已同步 |
| 速度 | 不能 | GPS + 盲区速度兜底 |
| 总里程 | 不能 | 对表基准 + GPS 增量 × 系数估算 |
| 电量% | 不能 | 静置电压查表 / 骑行按里程推算 |

## 结论三：本轮日志里抓到一个对表反弹的真实缺陷

11-24 07:55 对表记录：

```
ODO_SCALE learn: dash +71.00 vs app +75.00 -> ratio 0.9467; scale 1.2627 -> 1.1954 (first-fit)
ODO_ALIGN(main) app 11604.0 -> 11600.0 (meter) delta -4.00km base=11217 accum=312.00 trip=71.00
trip += -4.00km (odometer align; now 75.00)
```

07:58 重启开机：

```
state v=NaN src=0 soc=NaN km=75.06 ... odo=11604.1
```

对齐后被压到 11600.0，重启又弹回 **11604.1**。根因：**本次里程存在两份副本**——界面 `HudState.tripKm`（快照 71.00）与服务端 `TripTracker` 持久积分器（当时 79.00，5 秒落盘节奏还没写回）。对表时：

1. 界面拿**陈旧的内存副本**算 `accum = target − base − trip`；
2. 广播 `TRIP_ADD` 差额，服务端按**自己的副本**扣减并落盘；
3. 两份副本扣完仍对不上，重启回读服务端副本，对齐时减掉的那 4km 又回到总里程。

修法方向（下一版）：对表改为以持久账本为唯一基准，服务端走 `setKm(目标值)` 直接覆盖并立即 flush，而不是"内存副本 + 广播加差额"；`accum` 用覆盖后的目标 trip 反算。
