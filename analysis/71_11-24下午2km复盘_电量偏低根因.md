## 2. 「72.5V 只有 33%」的链条（逐环节定位）

1. **上一箱收车锚点偏低**。11-24 12:10 收车静置 70.6V，查表 28%，作为锚点落盘；那个样本离收车很近，可能还带一点残余压降，70.6V 在表里已经压到 28%（中段表：70.6=28 / 72.1=41 / 72.6=50）。
2. **App 被杀 2h 后恢复旧账本**。14:25:34 `restored last soc=33 (2h ago)`；`SocTracker` 从 prefs 回灌 `anchorSoc / anchorKm / perKmPct`，没有新电压依据就沿旧锚点往下推。
3. **本次里程没清零**：21.26 直接带进这一段。锚点里程同口径，predict 按 `anchorSoc − perKm × (km − anchorKm)` 继续扣；0.85km ≈ −1.1 点，33 → 31。
4. **骑行段压根不看电压**（BleService 1859–1861）：`!atRest` 时 `socVal = predict(tripKm)`，带载端电压被排除——这是 v1.0.53 为防「爬坡压降当掉电」定的。所以屏幕上 72.5V 是电压格的数，电量格完全走里程账本。
5. **静置纠正也抬不上去**。14:27:16 静置电压口径 56% vs 账本推算 31%，差 +25 点 > `maxAnchorJumpPct=12`，`anchorRestGuarded` 记一次 reject；按旧逻辑 reject<3 直接守住里程口径，向上纠偏要连续 3 次、每次最多 3 点。本次只有这一个静置样本，锚点原地不动。
6. **铅酸静置回弹**：电池放了 2h，端电压从 70.6 回升到 72.84V；查表 56%。账本没有跟着回弹对齐。

红字横幅「电量已耗尽·请充电」**不是**空电锁（emptyLatch）、也不是低电电压提醒；它来自里程格副标题 `range < 1f` 分支——`estRange` 硬顶后 `rangeKm=0` 触发。根因还是账本 SOC 被压低，续航跟着被算没。

## 3. 用户判断与工程事实的对照

用户主张：**剩余电量主要看电压，里程只作参考**；充电没充满、本次里程没清零都会把里程算进去，导致电量被打折。

- 同意的部分：账本锚点确实会**沿用上一箱的低值**，半充电之后没有干净的满电锚点，里程继续扣就把 SOC 越算越低；静置 OCV 是目前唯一不依赖里程的独立读数，应当在静置时拥有更高话语权。
- 不能照搬的部分（历史反例，analysis/57/62/64）：
  - 骑行带载压降 3–6V，瞬时 58–69V 乱跳，直接查表会出现 51%→17% 的横跳；
  - 中段 72–73V 是一条近平平台（30% 的电对应 1.3V），光看电压在这段分不清还剩多少；
  - 末端电压塌陷：66.2V≈4% 时还能骑十公里，底部无条件信电压会重演「0% 还能跑十公里」。

**折中方向**：静置 OCV 向上对齐放宽（电池比账本高，说明之前估低了，该抬）；向下纠偏维持原有的慢挪 + 预算 + 三次确认（防末端塌陷和系统性偏低）；骑行段仍走里程账本，但低负载滑行时的回升通道放宽一点。里程只做账本推算的参考系，不再让旧锚点把电量一路拖到底。

## 4. v1.0.63 改动清单（App / 只读侧，不碰写路径）

1. **静置锚点向上纠偏放宽**：`anchorRestGuarded` 里 `socRest > pred`（电压口径偏高）时，一次静置允许向电压方向抬最多 10 点，不再走「三次 reject 才挪 3 点」；向下方向逻辑原样保留（3 点/次、12 点一箱预算、三次确认），不参与 %/km 学习。
2. **回升预算放宽**：`recoverUp` 一箱总预算 10 → 16 点；门槛（45 秒持续、4 点死区、5 秒间隔、1 点/次）不变，防噪声抬高。
3. **电量 UI 改仪表盘格子条**：电量格内加 10 段电池条，已充段按 `socColor` 着色，空段暗灰；旁边仍保留大字号百分比。普通模式与 lite 模式同步。
4. 口径副标题保留「停稳·按电压 / 骑行·按里程推算」，让骑手知道当前这个数由谁算出来。
