# v1.0.13：蓝牙"反复断开重连"的两个真凶（这次有日志证据）

上一版修了 GPS/权限，这版回到你最早抱怨的那条：**蓝牙多次断开重连、不稳定**。

## 证据（来自你自己的日志）

```
raw_20261117_221542.csv
1794924973873,GAT,DISCONNECTED,reason=10 afterMs=30077
1794924990916,GAT,DISCONNECTED,reason=10 afterMs=0
1794925009968,GAT,DISCONNECTED,reason=10 afterMs=0
1794925067089,GAT,DISCONNECTED,reason=10 afterMs=0
1794925100138,GAT,DISCONNECTED,reason=10 afterMs=0
1794925131202,GAT,DISCONNECTED,reason=10 afterMs=0
```

统计全部 12 份日志：**6 次断连，100% 是 reason=10**，其中 1 次是"连上 30 秒后被踢"，
5 次是"连接根本没建立起来"（`afterMs=0`）。

`reason=10` = HCI **0x0A Connection Accept Timeout** —— 手机发出了连接请求，
**控制器没有应答**。含义很明确：控制器那边还残留着上一条链路的"已连接"状态，
它暂时不广播、也不接受新的连接。

## 真凶 1：autoConnect 配了 15 秒超时（自相矛盾）

```java
manager.connect(dev)
        .timeout(CONNECT_TIMEOUT_MS)   // 15 秒
        .useAutoConnect(auto)          // 系统挂起连接，等设备可连
```

Android 的 `autoConnect=true` 语义就是**把连接请求挂起**：不设固定超时，
等对端重新变得可连时由系统自动完成（这是 BLE "开机自动回连"的标准做法，
Nordic 官方示例也是这么用的）。而这里同时给了 15 秒超时 ——
控制器通常要 20–40 秒才能把旧链路收干净（监督超时 + 它自己的看门狗），
**15 秒必然在它变可连之前把请求取消掉**，于是每次都白撞一个 0x0A，
退避 17→19→57 秒后继续撞，看起来就是"一直在重连、一直连不上"。

**修法**：`autoConnect` 时超时给 **90 秒**；快连保持 15 秒。
并发判定（防重复连接）的预算也跟着对齐（快连 20s / auto 95s）。

## 真凶 2：扫描的 12 秒超时回调在"连上之后"还在跑

```java
h.postDelayed(() -> {
    stopScan();
    directAttempts = 0;
    retryLater(3000L);      // ← 连上以后这一行照样会执行
}, SCAN_TIMEOUT_MS);
```

情况是：扫到设备 → 立刻连上 → **但那个 12 秒的定时任务没人取消** →
12 秒后它跑一遍，末尾又排一次 `retryLater(3000)` →
3 秒后 `connect()` 就去碰一条**已经在正常推送数据的 GATT** →
库把它当成"重连"，对端则直接把这个连接踢掉。

这正好对上你看到的"连上十几秒就断一次"的节奏。

**修法**
1. `connect()` 顶部加两道闸：`ready && manager != null → return`（已经在流就别碰）、
   `connecting`（正在进行中就别叠加，但超过预算视为卡死、允许重试）。
2. 扫描超时回调里加同样的判断，连上/正在连就直接 return，不再排重连。
3. `retryLater()` 里也挡一次。
4. `reconnectNow()/stop()` 现在只清"连接任务"，不再把保活任务的回调一起清掉。

## 顺带：把重连任务做成固定 Runnable

以前每次 `h.postDelayed(this::connect, …)` 都是新 lambda，`removeCallbacks` 删不掉 ——
`start()/reconnectNow()` 之后旧队列里的 connect 还会照跑一次，形成**两条并发连接尝试**，
对端只认一条，另一条把链路踢掉。现在固定成 `connectTask` 字段，能精确取消。

## 顺带：断连原因说人话

日志和 HUD 上以前只有一个数字 `reason=10`。现在带解释：

| 码 | 含义 |
|---|---|
| 0 | 正常关闭 |
| 8 | 连接超时（信号弱） |
| 10 | 0x0A 控制器没应答连接请求 |
| 19 | 对端主动断开（控制器踢的） |
| 22 | 本机主动断开 |
| 62 | 连接建立失败 |
| 133 | GATT 错误（常见：小程序占用） |

以后日志里一眼就能看出"是车自己踢的"还是"我们这边的问题"。

## 车上怎么验（重点看两件事）
1. **连上之后 15–30 秒内不要断**。以前这个时间点几乎必断一次；现在应当稳。
2. 万一断了，看 HUD 底部那行 `断开(10(0x0A) 控制器没应答…)` —— 如果一直刷这个码，
   说明控制器那边的旧链路一直没收干净（那是它固件的问题，不是 App 能改的），
   我们能做的是**等够 90 秒让它自己恢复**，而不是每 15 秒去撞一次。
3. 如果日志里出现 `reason=19`，那是控制器主动踢（它有自己的看门狗），
   属于对端行为，只能靠回连速度弥补（现在是 1.5 秒回连）。
