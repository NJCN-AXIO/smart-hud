# 实车日志分析：67B 帧里到底有没有电压（2026-11-17）

数据来源：用户手机导出的 9 份 `raw_20261117_*.csv`（08:46 – 11:18，含 10:05–10:39 那趟十几公里）。

---

## 1. 硬事实：所有帧都是 67 字节，且 61 个字节从头到尾不变

| 项目 | 数值 |
| --- | --- |
| 总帧数 | 2983 |
| 服务/特征 | 全部来自 `0xFFF6`（`{0x0000FFF0-…}` 通知），**AE02 一条都没有** |
| 帧长 | 全部 67 字节 |
| 帧头 | 全部 `C9 9C`，`[2..3] = 94 05`（=71.4V 若按 ×0.05 解） |
| 全程不变的字节 | 67 个里 **61 个**（含 `[2..3]`） |
| 真的变过的字节 | `[42]`、`[47]`、`[61]`、`[63]`、`[64]`、`[65]` |

`[64]`、`[65]` 取值种类分别是 212 和 256 种 —— 这是**随机/校验/计数器**级别的变化，不是物理量。
`[47]` 只有 3 种（`E9` 2482 次 / `2F` 467 次 / `69` 34 次），`[63]` 只有 6 种。

**结论**：这一路通知里**没有电压、没有电流、没有速度**。一趟跑了十几公里、电压本该从 78V 掉到 72V 左右，
帧内容却一个字节都没跟着动。所以：

- `[2..3] = 94 05` 是**常量**，不是电压（之前"候选映射"的怀疑在这里被证实：它不可能随电量变化）；
- 无论怎么调 offset / 系数 / 大小端，**都解不出电压**；
- 我们坚持"扩展帧不套 20B 映射"这个决定是对的（否则会一直显示 71.4V 这个假数）。

## 2. 另外两条路也走不通（本轮实测证据）

| 通道 | 属性 | 实测结果 |
| --- | --- | --- |
| `0xFFF4` | `props=0x02`（READ） | 连上后我们读了一次，**75 次全部返回空**（日志 `READ 0xFFF4` 后面无数据） |
| `0xFFF7` | `props=0x06`（READ + WRITE_NO_RESP） | 本轮已加入"所有可读特征都读一遍"，下次日志会看到 |
| `0xAE01` / `0xAE02` | WRITE_NO_RESP / NOTIFY | 订阅后**一次通知都没来**（2983 帧里 0 条 AE02） |

## 3. 连接为什么"多次断开"——实测是每 14–17 秒被对端踢一次

| 指标 | 数值 |
| --- | --- |
| 连接成功 | 82 次 |
| 断开 | 85 次（`reason=0` 80 次 = 对端主动关闭） |
| 单次连接时长 | 中位 **14.1 s**，最长 17.0 s，80 次里 73 次落在 10–15 s |
| 连接尝试 | 155 次（其中 76 次 `status=-5` 失败） |
| 帧率 | 1.25 Hz |

这不是"信号弱"的随机掉线，而是**到点就断**：每次连上约 15 秒、对端关闭、我们再连。

对照抓包原件：微信小程序那次会话持续了 **45 秒以上**（两次 67B 写包间隔 45 秒）且没被踢。
差别只有一个 —— **小程序会往 `0xFFF5` 写 67 字节的查询包**（t=339.7s / 384.6s 各一条），我们全程只写 CCCD。

也就是说：控制器很可能要求"15 秒内收到一次合法命令"，否则主动断开。
在"绝不向控制器写数据"这条红线内，这个断连**无法根治**，只能做到"断了立刻回连"。

## 4. 顺手抓到的程序 bug：日志被刷爆

`raw_20261117_100526.csv` 9.1 MB / 174,848 行，其中 **171,634 行是同一条 SYS**：
`conn: 扫描附近设备…`（23 分钟 ≈ 122 条/秒）。

后果：① 真帧被淹，分析要先过滤 17 万行；② 写盘耗电；③ 日志 16 MB 上限很快触发轮转，历史被冲掉。

改法（v0.6.3）：同一句状态只记一次，通知栏最多 2 秒刷一次，CSV 里 5 秒一条封顶。

## 5. 由此得到的结论

1. **"解 FFF6 的通知帧拿电压"这条路，到此为止是死路**：帧里没有这个物理量，不是我们没解对。
2. 微信小程序能显示实时电压，只能来自 **写命令后的响应**（或另一条需要命令触发的通道）。
   在没有写权限的前提下，App 拿不到控制器内部电压。
3. 因此接下来只有三条路（见对话里的选择）：
   - A. 硬件采集电压（电阻分压 + ADC / INA226，蓝牙模块发出来）——最可靠，不看控制器脸色；
   - B. 放开"只读查询包"（仅发与小程序同款、不改变任何设置的查询帧）——能拿到真值，但要承担未知语义风险；
   - C. 维持只读，电压靠"手工哨点 + 里程推算"——现在就是这条路。

## 6. v0.6.3 为下一步埋的观测点

- 所有可读特征（`FFF4`/`FFF7`/`2A00`…）连上即读一次，**值全 hex 写进 `GAT` 行**（`READ-PLAN readable=N` 表明读了几个）；
- 每次断连记 `DISCONNECTED reason=N afterMs=M`，一眼看出这次连了多久；
- 断开后**复用同一个 GATT 直接回连**（不再销毁重建），配合 `autoConnect` 让系统等控制器重新广播；
- 状态文案去重，日志里终于能直接看到帧而不被 17 万行噪声淹没。
