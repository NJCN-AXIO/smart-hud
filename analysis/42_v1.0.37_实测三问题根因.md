# v1.0.37：实测三个问题，全部定位到根因

这一版不猜，全部从你 14:03–14:17 的日志和截图里定位。三件事各自有明确的代码行。

## 一、闪退：开机约 3 分钟必崩 —— `Padding must be non-negative`

日志里的堆栈（6 份文件里出现 3 次，间隔都约 2 分 50 秒）：

```
java.lang.IllegalArgumentException: Padding must be non-negative
    at androidx.compose.foundation.layout.PaddingElement.<init>(Padding.kt:336)
    at com.hud.delivery.ui.HudScreenKt.HudScreen(HudScreen.kt:226)
```

根因：OLED 防烧屏每 90 秒把内容挪一次，四档位移是 `0/3/-3/2`。其中 **-3dp 那一档**用的是
`.padding(horizontal = -3.dp, ...)` —— Compose 的 padding 不允许负值，一到这一档就抛异常。
所以现象是"固定几分钟后闪退"，而不是随机。

修：改用 `.offset(x, y)`（offset 本来就允许负值，语义也更对：只挪不改布局尺寸）。

## 二、断开连接后 100% → 29%，"还能跑 ~30km"

两个独立的错，叠加在一起。

### 错 1：断开后冻结的是几小时前的旧值（不是刚看到的值）
v1.0.30 把电量改成"连上就直读"之后，直读分支只往账本写锚点，**不再推进 `shown`**；
而断开分支取的正是 `socTracker.getShown()`。于是"连着时 100%、一断开 29%"。

证据（14:11:39 的 REC 行）：
```
rv=71.84 v=74.22 vm=79.12 dc=74.22 src=1 sag=3.54 spd=18 soc=100 sra=47 rng=30.3
```
`soc=100` 是显示值，`sra=47` 是"这一帧原始电压直接查表"的结果 —— 两者差 53 点。

修：新增 `lastLiveSoc`，每次直读算出来的值都记下来；断开就冻结它，不再取账本旧值。

### 错 2：手机里存着一个 `3.3%/km` 的毒样本
`rng=30.3` 在 `soc=27` 时意味着满电只有 ~30km —— 这来自老版本被带载压降骗过的那几趟学到的
`perKmPct=3.3`，它一直存在手机上，新版本修好电压口径也照样按 3.3 算续航。
正常 21Ah/72V 是 1.2–1.3%/km。

修（两道）：
1. 启动时若读到 `>2.0%/km` 就判定为旧口径毒样本，清掉重学（会落一行 `per_km ... looks poisoned`）。
2. `perKmOrDefault` 不再只做绝对封顶，而是**以用户填的满电续航为准**，只允许落在
   `0.4× ~ 2×` 预期值之间（80km → 0.5 ~ 2.5%/km）。满电续航是你给的硬事实，比任何历史样本可信。
   新增 3 条单测。

### 顺便：电压整体被抬高了两格
```
rv=71.09 v=74.78 vm=78.84 dc=74.78 sag=3.71 thr=2.56 spd=22
```
`vm`（真正拿去查表的电压）是 78.84V，而这一帧原始只有 71.09V。原因是 45 秒窗取的是 **0.9 分位**，
假定了"这个字段只会偏低（带载压降）"；但实测同一分钟内 `rv` 在 71.1–74.9 之间走、`vx=78`，
**向上也有尖峰**（截图里连 80.2V 都上过屏）。0.9 分位等于专门挑尖峰。

修：三个滤波器全部分位 `0.9 → 0.5`（中位数），并对逐帧压降补偿封顶 2.5V。
代价是比"最轻载那一帧"低 0.5–1V，但不会再把 73V 显示成 100%。

## 三、没骑车、拿着手机走路，也显示时速、里程在涨

根因：里程和时速**只信 GPS**，从来没问过"控制器还连着吗"。

修：引入 `linkFresh`（15 秒内收到过控制器帧）。`linkFresh=false` 时：
- 不累计里程（只把距离基准点挪过去，避免重连那一下蹦出假里程）；
- 时速直接显示 `--`，并 reset 速度滤波器（否则"丢点保持 4 秒"会把走路最后那 2km/h 留在屏幕上）；
- 隧道补里程（GapFill）也跳过。

这台车仪表的前提就是"手机在车上、车通电"。断开就冻结，比猜一个速度更诚实。

## 四、关于"总里程才 30KM"
