# 09｜第二轮深挖：里程会翻倍、补里程其实没生效（v0.9.1）

> 这轮不看"能加什么功能"，只看"已经在跑的逻辑里哪几处会算出错数"。
> 找到 4 处，全部有代码依据或单测反证，不是猜测。

## 1. 隧道/桥洞的"补里程"会被 GPS 再算一遍 → 里程翻倍

`onLocationChanged` 里两段逻辑互相踩：

```
① 断档补点：gpsKm += 断档前速度 × 断档秒数      (GapFill，3–15 秒才补)
② 两步累计：trackDist.add(新点) 从上一个点算直线距离，也加进 gpsKm
```

①②对**同一段路**都加了一次。8 秒断档、20km/h 时，真实位移 40m，账上会变成 80m。

**修法**：`:core TrackDistance` 新增 `rebind(tMs, lat, lon)`——只把基准点挪到当前位置、
**不计里程**。补点之后先 rebind，再喂同一个点，`add()` 自然返回 0。

单测三条锁死：
- 补完再喂同一点 → 返回 0.0（不能重复计）
- 不 rebind 时同一段 40m 会被完整计入（反证 rebind 的必要）
- rebind 不影响 `totalM`（只是挪基准，不是改总账）

## 2. 补里程其实大部分时候没生效（更隐蔽的老 bug）

`GapFill.meters(gap, speedStab.value())` 用的是**平滑后的显示速度**，
而 `SpeedStabilizer` 的保持期只有 **4 秒**（`holdMs=4000`）。

也就是说：
- 断档 3–4 秒 → 还能拿到速度，补得动
- 断档 5–15 秒 → `speedStab.value()` 早就归零 → `GapFill.meters` 返回 0 → **一段都没补**

**修法**：改用"断档前那个点自己的工作速度"——`lastLoc.getSpeed()*3.6`，
没有就退回 `speedStab.value()`。日志里也改成打印实际用的速度。

## 3. 速度兜底公式没有上限

GPS 不给速度时用位移兜底：`d/dt × 3600`。过滤条件是 `d ≤ 200m`、`dt ≥ 500ms`——
合起来允许 **200m / 0.5s = 1440km/h** 通过，再喂给 1€ 滤波，会让时速表瞬间飙到天上。

**修法**：算出超过 100km/h 一律丢（真实电动车不可能），保持 NaN 让下一层兜底。

## 4. 133 风暴时每 4 秒硬撞一次

日志里 133（`status=-5`）是成串来的。原逻辑：133 → `retryLater(4000)` 固定 4 秒，
撞一次吃一串，再撞再吃——连接次数和电量都烧掉。

**修法**：133 走独立指数退避 **4s → 8s → 16s → 24s**，连上后 `done()` 归零。
普通断开仍走 2→4→8→15s，`reason=0`（对端主动关）仍 1.5 秒快回连（那条是实车验证过的）。

## 5. HUD 屏幕亮度：正午看不清，夜里刺眼

屏幕常亮 + 沉浸式全屏都已具备（这轮核查通过，不用改），但亮度完全交给系统：
车把上正午强光下 30% 亮度基本读不出数字，夜里 100% 又晃眼。

**修法**：读环境光传感器（`TYPE_LIGHT`，无需权限），按 lux 分四档设置窗口亮度：
`<10 → 0.35`、`<200 → 0.6`、`<2000 → 0.85`、`更强 → 1.0`；没有传感器则固定 0.85。
`onResume` 注册、`onPause` 注销，变化小于 0.1 不重设窗口参数。

## 6. 核查通过、无需改动的项

| 项 | 结论 |
|---|---|
| 屏幕常亮 | `FLAG_KEEP_SCREEN_ON` 已设 |
| 沉浸式全屏 | Android 11+ / 10- 两套分支都在 |
| 本次里程持久化 | `TripTracker` 每 5 秒落盘，进程被杀后能接上 |
| 静止 GPS 漂移 | `TrackDistance` 低速+小位移判抖动，不计也不丢点 |
| 帧解析开销 | 2Hz × 67B 解扰，分配可忽略 |
