## 一、结论先行

**这份日志拿不到电压和速度的字段映射。** 原因是数据侧缺“变量”，不是解析方法的问题：

- 整场会话里，控制器的通知帧 **只出现过 1 种内容**（20 字节，重复 91 次，逐字节完全相同）；
- 日志里**没有任何一次“读取”请求**，全部数据都来自同一个通知通道；
- 帧内有 4 组重复的连续字节，更像**静态参数/状态块**，不像实时遥测。

没有变化的样本，就没法做“已知 69.7V / 25km/h × 对应字节”的比对——这是字段逆向的硬前提。

好消息是：**协议的外壳已经全部摸清了**（服务、特征、句柄、速率、帧头、帧长），下一轮只要抓到“数值在变”的数据，定位字段就很快。

## 二、文件格式

- 标准 btsnoop（magic `btsnoop\0`，version 1，datalink 1002 = H4），**大端字节序**。
  （一般脚本若按小端读会在第 1 条记录后就停住，`tools/parse_btsnoop.py` 已按大端实现。）
- 时间戳是 Android 的“自公元 0 年起算秒”，不是 Unix 时间；记录顺序也存在乱序。
  实际跨度约 **71 分钟**（`max_ts - min_ts ≈ 4293 s`）。

包型统计：

| 类型 | 数量 |
| --- | --- |
| HCI Event | 6,414 |
| HCI Command | 1,582 |
| ACL | 8,436 |

ACL 按连接句柄分布：

| 句柄 | ACL 包数 | 说明 |
| --- | --- | --- |
| 0x0EDC (3804) | 7,576 | 另一条连接，L2CAP 层不是 ATT/SMP，非本次目标 |
| 0x0003 | 545 | 另一条连接（经典蓝牙侧流量） |
| **0x0005** | **315** | **本次目标：控制器，ATT 层，131 个 ATT 帧** |

即：**98% 的流量跟控制器无关**，这也是“直接把 hex 丢给大模型”效果差的原因——噪声比信号多两个数量级。

## 三、控制器链路（这才是有效部分）

连接句柄 **0x0005**，全程 ATT。

### 3.1 GATT 地图

| 服务 | 范围 | 特征 | 属性 | 说明 |
| --- | --- | --- | --- | --- |
| 0x1800 Generic Access | 0x0001–0x0003 | 0x2A00 | Read | 设备名（本次未读） |
| **0xFFF0**（厂商自定义） | 0x0004–0x000D | **0xFFF4** | Read | handle 0x0006，疑似型号/版本 |
| | | **0xFFF5** | Write / WriteNoRsp / Notify | handle 0x0008，**下行通道**（App 往控制器写） |
| | | **0xFFF6** | Read / Notify | handle 0x000A，**上行通道**（控制器推数据），CCCD = handle 0x000B |
| 0xAE00（厂商自定义） | 0x0080–0x0085 | 0xAE01 | WriteNoRsp | handle 0x0082 |
| | | 0xAE02 | Notify | handle 0x0084，本次会话**从未订阅** |

> 这组 `0xFFF0 / 0xFFF4 / 0xFFF5 / 0xFFF6` 是国产蓝牙模块最常见的“透传”服务模板。

### 3.2 会话时间线（相对日志起点）

| 时间 | 事件 |
| --- | --- |
| 338.18 s | 开始服务发现：`0x2800` / `0x2803` 读取 |
| 338.48 s | 发现 0x1800、0xFFF0、0xAE00 三个服务 |
| 338.62 s | 读到特征表：FFF4(props 0x02)、FFF5(props 0x0E)、FFF6(props 0x12) |
| **338.80 s** | 向 handle 0x000B 写 `01 00` → **开启 FFF6 通知**（全程唯一一次 CCCD 写） |
| **339.14 s** | 第一条通知到达，此后稳定 **~2 Hz**（间隔 0.47–0.62 s） |
| **339.71 s** | 向 handle 0x0008 写 67 字节 |
| 340 – 384 s | 持续收到 91 条通知，**内容全部相同** |
| **384.63 s** | 第二次向 handle 0x0008 写 67 字节 |

### 3.3 通知帧（FFF6，20 字节）

```
C9 9C 94 05 59 59 69 59 6A 81 1E 4D 75 75 75 75 1D 1D 1D 1D
 ^头^  ^^ ^^  |        |            | 4×0x75  | 4×0x1D
```

- 帧头固定 `C9 9C`，定长 20 字节，2 Hz。
- `75 75 75 75` 与 `1D 1D 1D 1D` 是两组连续的重复字节 → 像是 4 路同构量（4 个通道 / 4 组参数），或按字节排列的静态参数块。
- 整场 91 帧零变化。电压 45 秒内一动不动到 0.01V 都合理，但**速度字段不可能也不动**，所以基本可以判定：**这个通道在本次会话里只发了静态/握手类内容，没进实时页面**。

### 3.4 已知字段候选（待验证，不要当成结论）

按“边界对齐 + 系数干净”筛，最像一个电压的两个位置：

| 候选 | 原始值 | 系数 | 结果 | 可信度 |
| --- | --- | --- | --- | --- |
| `bytes[2..3]` LE uint16 | 0x0594 = 1428 | ×0.05 | **71.4 V** | 落在 72V 铅酸量程内，系数是常见 0.05V/LSB |
| `bytes[2..3]` BE uint16 | 0x9405 = 37893 | ×0.0019 | 72.0 V | 需要非整数系数，不太像 |
| `bytes[0..1]` BE | 0xC99C = 51612 | ×0.0014 | 72.3 V | 头两字节被当数据用，与 `C9 9C` 帧头矛盾 |

第一行是目前唯一“**量程对、系数整、位置对**”的组合（1428 × 0.05 = 71.4 V）。
但它连续 45 秒不变，无法确认。**验证方法：把电池放到 ~68V 左右再抓一次，看 1428 是否变成约 1360。**

### 3.5 那两条 67 字节写入

两次写入仅 3 个字节不同：

```
第 47 字节：0x69 → 0xE9
第 64、65 字节：0x43 0x71 → 0x48 0xE6
```

并且**写入内容里嵌着当前那 20 字节通知帧**：

```
C9 9C 03 09 | 59 59 69 59 6A 81 1E 4D | 75 75 75 75 | 1D 1D 1D 1D | 25 81 25 7F | ... | E8 43 71 CC
             ↑ 与通知帧第 4–11 字节完全相同
```

这个形态高度像**挑战/应答（challenge-response）**：设备发一段随机块，App 回写“原块 + 计算出的签名”。
若真如此，后面的遥测数据很可能是**加密/扰动**过的，靠猜字节走不通 —— 那就得看小程序的实现代码（只读、不改包）。

**本次抓包无法区分“明文但没数据”和“加密”这两种情况**，这是下一轮要解决的问题。

## 四、这份日志还缺什么

| 缺口 | 影响 | 补救 |
| --- | --- | --- |
| 没有广播包 / 设备名 / MAC | App 里“固定 MAC 直连”没有依据；若控制器用随机地址，MAC 会变 | 重抓时从**连接前**开始录 |

## 五、下一轮怎么抓（30 分钟能出结果）

不再用 HCI 抓包（噪声大、取证难），改用 App 自带的原始帧日志：

1. 装 `app-debug.apk`，在设置里填控制器 MAC 或设备名关键字，连上；
2. 打开小程序，把**电压读数**记下来（精确到 0.1V）；
3. 回到 HUD，点“标记”，把刚刚那个电压填进去 → 存一条 `(帧字节, 电压)` 样本；
4. 让车**保持匀速骑行 1–2 分钟**，同时间隔标记几次（顺便填速度）；
5. 停车，再标记一次（速度 0）；
6. 把电量放掉一些（比如骑 5 km 或等电压掉 1V），重复第 3–5 步；
7. 用 USB 取 `Android/data/com.hud.delivery.debug/files/logs/raw_*.csv`；
8. 跑 `python tools/find_field.py raw_xxx.csv`。

脚本会自动遍历 偏移 × 位宽 × 字节序 × 系数，用你的标注电压做线性回归，按拟合度排名——**不需要人肉对着 hex 找规律**。

判据（很硬）：
- 拟合 R² > 0.98 且斜率落在 0.02–0.2 之间（0.1V/LSB 这类常见系数）→ 基本就是它；
- 只有 2 个不同电压时，任何 2 点都能拟合，所以**至少要 3 个不同电压、其中跨度 ≥3V**，否则结论不可信。

## 六、如果第二轮还是不动

那就说明数据不在 FFF6 的明文里（加密，或根本不在这条通道）。此时有两条退路，都比继续猜字节划算：

1. **看小程序代码**（只读、不改包）：解出 `wxapkg`，在 JS 里找 0xFFF6 的解析函数和密钥。改包跑起来是做不到的（微信有 MD5 清单校验），但读代码定位算法完全可行。
2. **绕开协议**：72V 电池并一个分压电阻到 ADC（或直接上 INA226 / 库仑计），自己做一路 BLE 广播电压；速度用手机 GPS。这样完全不依赖控制器协议，精度还更高。

## 七、追加证据：小程序三张截图（2026-11-16，20:06 / 20:42 / 21:06）

| 截图时间 | 电池电压 | 转把电压 | 故障提示 |
| :-- | :-- | :-- | :-- |
| 20:06 | **69.7 V** | 0.8 V | P档 |
| 20:42 | **71.4 V** | 2.4 V | （空） |
| 21:06 | **72.3 V** | 0.8 V | P档 |

三张都是「M1」页（版本 Y14），参数网格完全一致：
`电压选择 72V`、`P档 自动P档30秒`、`仪表协议 爱玛1`、`ABS 关`、`强制超速 关`、
`刹车 低电平`、`启动 标准`、`超速 5档`、`电流 默认`、`码数 100%`、`车型 两轮车`。

### 这三张图修正了什么

1. **电池电压确实是控制器通过蓝牙上报的实时值**。60 分钟内 69.7 → 71.4 → 72.3 单调上升，
   是充电过程。所以数据存在；上一轮抓不到，只是因为那条通道里的数值没有跨过一个分辨率台阶。
2. **「91 帧全同 = 心跳 / 参数块」这条结论降级为待验证**。
   充电时电压漂移约 0.04 V/分钟 → 45 秒理论漂移 ~0.013 V，
   **低于 0.05 V/LSB 的一个最低位**。帧逐字节相同，完全可以由「充电中静止」解释，不必然是心跳。
3. **数值巧合（目前最强的一条线索）**：按 0.05 V/LSB 换算，
   71.4 V ↔ 1428 = `0x0594`；而抓包帧 `bytes[2..3]` 小端正是 `0x0594`。
   这是唯一同时满足「量程对、系数整、位置对、且数值撞上一条真实读数」的候选。
4. **「仪表永远满格」更像参数问题而非协议不可解**：`电压选择` 已经是 72V（档位没设错），
   但 `仪表协议 = 爱玛1`。若该协议给仪表的电量刻度是按 60V 标定的，72V 包就会一直顶格。
   零成本试法：把 `仪表协议` 换其它选项逐个试，看实车仪表反应。

### 为什么还不能结案

截图只有电压数字，**没有同一时刻的帧字节**；日志文件名时间（20:36:56）与 20:42 那张截图相差 6 分钟，
且日志内部 ATT 会话在起点后约 338 s（该 log 的时间戳字段无法直接换算到墙钟，甚至存在乱序），
**无法建立时间对应**。一个点撞上，是巧合的概率并不低——必须用「帧里的数值真的动起来」来证伪。

### 判决性实验（下次必做，成本 5 分钟）

负载会让电压瞬间塌 1–2 V，远大于 0.05 V 的 LSB：

1. 连上 HUD → **拧油门 / 上路** → 看「原始帧」hex 是否开始变化；
2. 若变化 → 用「标记」采 4 组不同电压 → `python tools/find_field.py raw_xxx.csv` 按通道求解；
3. 若完全不变（尤其若 `AE02` 也没有数据）→ 实时遥测可能被扰动或根本不在 BLE 明文里，
   转「读小程序代码（只读不改包）定位算法」或「硬件直采电压」两条退路。

### 顺带确认

- `0xAE02` 在上次抓包里**从未被订阅**，而它是最可能的遥测通道
  （`FFF6` 那 20 字节里有 `75 75 75 75`、`1D 1D 1D 1D` 两组 4 连重复字节，很像固定参数块）。
- v0.2.2 起 App 会订阅**所有可通知特征**，并按通道分别落盘；
  下一份日志一定能回答「AE02 到底推不推数据」。
